# Country-localised bitocard.com stores: implementation plan

**Status:** Stage 1 shipped 22 October 2026 (`HouseService.storeFor`, lifted `StoreHostsService` skip, `country_stores` switch; behind the switch, off everywhere, no customer-visible change). Stage 2 shipped 22 October 2026 (the `houseStoreId` sentinel reclassified at every call site; see its table below), with a review follow-up the same day: `storeFor` now refuses to adopt a subdomain that exists but is not a house store (`subdomain_taken`), rather than silently treating whatever already holds the name as the country store. The subdomain format rule (minimum 3 characters) already keeps a reseller from registering a 2-letter code like `ng` through the normal create/rename path, so this was defence in depth, not a live exploit — but `storeFor` must never trust that alone once something else calls it. Stage 3 shipped 22 October 2026 (`StoreSellers`'s seller/mode/resolve routing fixed; see its section below for the second bug found and fixed along the way, and the storefront-catalogue gap found but left for Stage 4). Stage 4 shipped 22 October 2026 (the storefront-catalogue gap closed, root's redirect wired up, a second catalogue-scoping bug found and fixed along the way; see its section below). Stage 5 shipped 22 October 2026, **generalised to every market in the list by explicit instruction, not just the three pilots** — see its section below for what that changed about the stage's own original wording. **`country_stores` is still off everywhere in production**, and `HouseService.storeFor()` is now reachable from a real checkout for any market, but every piece built across all five stages is still exercised only by this plan's own tests until an admin switches a market on, so none of it is customer-visible yet.

This is the implementation source for giving bitocard.com country-localised subdomains (`ng.bitocard.com`, `gh.bitocard.com`, `ke.bitocard.com`, …), one per pilot market, each a fully local storefront (its own catalogue scope, currency, seller of record) hosted the same way a reseller's own store is hosted today. Where this plan differs from `AGENTS.md`, this plan is provisional until merged back into it; `AGENTS.md` wins on everything it already states unless this document explicitly supersedes a line of it (noted inline below).

## Why

A UK (GB) customer bought Nigerian MTN airtime on bitocard.com (a legitimate case: buying airtime for someone abroad) and checkout failed with `conversion_unavailable` ("Conversions to and from GBP are paused"). Root cause, traced in detail during planning: bitocard.com has exactly one global `Store` row (`houseStoreId`) and resolves the seller of record for every purchase as `HouseService.resellerFor(customer.country)` — the **buyer's** country's house account. `PricingService.context()` then prices against that seller's currency (`reseller.countryRef.currency`), so a GB buyer's purchase of an NGN-priced product is forced through a GBP pricing context even though the product itself never needed GBP at all. Same-country purchases already skip FX correctly today (`PricingService.convert()`'s early return when `from === ctx.currency`); the bug only bites when a foreign visitor's country forces a foreign currency context onto a domestic product.

**The fix is routing, not a new FX bypass.** Giving each pilot market its own store (seller of record fixed to that market, not to the visiting customer) means a purchase on `ng.bitocard.com` is always priced through the NG house account regardless of who is buying, so NGN products never need GBP (or any other buyer currency) to be healthy. Cross-border purchases (an NGN buyer paying for a KES product, or a GBP wallet paying an NGN price) still convert at payment time exactly as today — this plan does not eliminate FX, it eliminates *unnecessary* FX forced by buyer-not-product country routing.

## Product decisions (signed off)

- **Root `bitocard.com` redirects.** Once a market has a live country store, choosing that market in the signed-out market dialog (or being a signed-in customer whose fixed country has a live store) redirects into `<country>.bitocard.com` rather than setting the `bc_market` cookie and staying on root. Root remains the global discovery/market-choice shell permanently for any market **without** a live country store yet (so bitocard.com never regresses for un-piloted markets).
- **Customer accounts are not fragmented.** Unlike reseller stores ("an account at one store does not exist at another", `AGENTS.md`), country stores share bitocard.com's single existing customer pool. A customer's account is the same whether reached through root or their country's subdomain; only which store/seller context serves their purchases changes. This is a deliberate, documented deviation from the reseller multi-store isolation pattern — do not accidentally apply `CustomerGuard`'s per-store session scoping to country stores.
- **DNS mechanism is Cloudflare, not Vercel.** The original proposal named "the Vercel API to add the subdomain"; corrected during planning. bitocard.com's zone lives on Cloudflare (`AGENTS.md`, "Store addresses on bitocard.com"); Vercel's Domains API only adds a domain to the storefront's Vercel *project* for TLS/routing and cannot create the DNS record. Country subdomains are provisioned with the exact same two calls `StoreHostsService.sync()` already makes for reseller stores: `cloudflare.createRecord(...)` then `vercel.addToProject(...)`. No wildcard DNS or certificate, consistent with the existing "No wildcard record or wildcard certificate" rule.
- **Pilot markets are the existing three**: Nigeria, Ghana, Kenya, matching `AGENTS.md`'s pilot markets. No other market gets a country store until these three are validated in production through a full billing/payout cycle.
- **No new Prisma tables.** Country stores are `Store` rows (the existing multi-store/template machinery from M14b), owned by each market's existing house `Reseller` row, with `template: 'all_in_one'`. The schema already supports this; several specific call sites that assumed exactly one house store do not (see Stage 2).

### 3. Pricing/seller routing fix — complete (22 October 2026)

This is the change that actually closes the GB/NGN bug.

- [x] `StoreSellers`: `resolve()` previously 404'd *every* house store (`store.reseller.house`), including a country store — so nothing could ever reach a country store through the request path (`BitoCard-Store: ng`) at all. It now refuses only the single root store by ID (`isRoot`), the same pattern Stage 2 established elsewhere; a country store resolves exactly like a reseller's (published, reseller not suspended).
- [x] `isHouse()` is now "any house store" (root or a country store), matching Stage 2's own reclassification elsewhere in the codebase (catalogue listing scope, template bypass, the crypto desk) — those callers already expected this and needed no further change. A new, private `isRoot()` captures the one place that must still mean *only* the single root store: "the seller depends on the buyer's own country."
- [x] `mode()`: every house store (root or a country store) now shares BitoCard's single Customer-checkout Sandbox switch (`house.mode()`), never the Prisma-default `checkoutMode` column on the `Store` row. This fixes a second, closely related bug Stage 1 introduced without noticing: `storeFor()`'s `prisma.store.create()` never set `checkoutMode`, so every country store defaulted to `test` (the schema default) with no way to flip it live — `mode()` would have reported a country store's checkout as sandboxed forever. `storeFor()` now also writes `checkoutMode: 'live'` explicitly, so direct reads of the raw column (`stores.service.ts`'s presenters) are truthful too, even though nothing live-reachable reads it for a house store's actual checkout.
- [x] `seller()` / `sellerFor()`: on the single root store, unchanged (the house account for the *buyer's* country, since root has no country of its own). On a country store (`isHouse(store) && !isRoot(store)`), always that store's own house account (`store.resellerId`), never the buyer's — skipping the independent-reseller checks (suspended, unverified, live-not-active) that don't apply to BitoCard's own accounts. On a reseller's store, unchanged.
- [x] Hardened `HouseService.storeFor()` while in the area: it now refuses to adopt a subdomain that already exists but isn't a house store (`subdomain_taken`), the same ownership check added after the Stage 1/2 review (see the Status line above).
- [x] `test/country-stores.test.mjs` (new file), 4 tests:
  - Reproduces the exact reported bug: a GB customer, signed up and buying on `ng.bitocard.com`, with GBP given no `CurrencySetting` or `ExchangeRate` row at all (so any attempt to convert to or from it fails outright) — the NGN-priced purchase completes, and the resulting order's seller is NG's own house account; no GB house account is ever created.
  - Confirms root bitocard.com's own behaviour is unchanged: the same GB customer buying the same product on root (with GB's categories and payment methods now configured so the purchase reaches pricing) still hits `conversion_unavailable`, because root still resolves the seller from the *buyer's* country — proving Stage 3 only changed country-store routing, not root.
  - Confirms a country store's checkout reports `live`, not sandboxed, by default (the `checkoutMode` default-value bug above).
  - A genuine cross-border case that must keep working: an NG customer on `ng.bitocard.com` buying a USD-face product still converts normally (live NGN/USD rates present) — proving this stage removes *unnecessary* FX only, not FX itself.
- [x] Full regression: build and lint clean; every suite touched by this stage and Stage 1–2's (store-hosts, settings, checkout, hosted-checkout, customer-wallets, order-access, manual-top-ups, p2p, stores, store-templates, support tickets/chat/chat-files/bots, exchange, exchange-desks, openapi-docs) passes.
- [ ] **Found during Stage 3, left for Stage 4, not yet fixed:** `apps/api/src/storefront/storefront.service.ts`'s `StorefrontService.inStore()` has the exact same "reject every house store outright" gate `StoreSellers.resolve()` had (`store.reseller.house` → 404), and it is the function behind `GET /v1/storefronts/:subdomain`, `GET /v1/store/home`, `GET /v1/store/products` and every other catalogue/home-page read the storefront app makes for a hosted store. Fixing `StoreSellers` was enough to make *checkout and customer accounts* work on `ng.bitocard.com`, but the store's actual pages (home, catalogue, product listings) would still 404 until `inStore()` gets the same `isRoot`-not-`isHouse` treatment. This belongs to Stage 4 ("storefront routing"), not Stage 3 ("pricing/seller routing"), but must not be missed: without it, nothing in Stage 4's redirect-and-render plan can actually work end-to-end. `inStore()` also assigns `scope.mode: store.checkoutMode` raw (the same column-default bug `StoreSellers.mode()` had) — once its house-store gate is lifted, that assignment needs the same `isHouse(store) ? house.mode() : store.checkoutMode` fix, not a bare column read.
- [ ] **Flagged, not acted on — a product decision, not a bug:** `support/tickets.service.ts` and `support/chats.service.ts` route a house-store ticket/chat's `resellerId` by `house.resellerFor(customer.country)` (the *buyer's* country) whenever `house` is true, which after Stage 2's generalisation is now true for a country store too, not just root. This is the identical "buyer's country, not the store's" pattern Stage 3 just fixed in `StoreSellers` — but support routing isn't pricing, and the plan's own Stage 2 table explicitly called this "already handles the multi-market case" (i.e. intentional: support resellerId is bookkeeping for which house account's queue a ticket sits in, not a seller-of-record/FX concern).
